# OAuth Setup Guides

A library of ready-to-use guides that show developers how to create an OAuth
app with a provider and get it approved, so their AI agent's users can connect
that app. A developer can look up an app, get a guide they can follow and
share, and know exactly what will block them and how long approval takes.
They can also submit an unfamiliar app and have a research agent generate its
guide live, using the documented pipeline in `research/agent-brief.md`.

The library holds **109 guides**: 6 researched, reviewed, and published, and
103 generated by the agent pipeline and kept as `draft` until individually
spot-checked (see Limitations).

## How to use this

### If you are a developer connecting an app (the hosted site)

There is nothing to install. The site is a static page (HTML, CSS,
JavaScript); all guide data is embedded in the page.

1. **Browse or search the library.** The home page lists every guide with a
   difficulty badge. Use the search box or the category filter chips to
   narrow by product area (CRM, payments, project management, social, HR,
   and more).
2. **Compare before you commit.** The comparison table puts all 109 providers
   side by side: difficulty, active work vs waiting time, and whether provider
   approval is required. This is the fastest way to spot the providers whose
   approval process will dominate your timeline.
3. **Open a guide and follow it top to bottom.** Each guide page has:
   - a difficulty rating and a time split (your active work vs provider
     waiting time, never merged into one misleading number);
   - an **approval panel**: whether review is required, what triggers it, any
     pre-approval caps, cost, and the wait, quoted from the provider where
     the provider states it;
   - the **recommended app flavor** (for example, which OAuth grant or app
     type to create) and the alternatives;
   - prerequisites, then numbered steps, each badged **You**, **Agent**, or
     **Either**, so it is clear what an AI agent can do for you and what only
     a human account holder can do;
   - **blockers** with how to clear each one, and nuances that bite later
     (token rotation traps, one-way-door choices, expiring permissions);
   - an **evidence section**: what was tested, the official sources read, and
     what remains unverified, plus a last-verified date and a status badge
     (`published` or `draft`).
4. **Share a guide.** Use the copy-share-link button on any guide page to
   send a developer straight to that guide.
5. **Request a guide that is not there.** Use **Request a guide** and submit
   an app name or website. The request is stored in your browser
   (localStorage); the site operator runs the agent loop below and the new
   guide appears in the library marked `draft` until reviewed.
6. **Check the methodology page** if you want the difficulty rubric and the
   effort-honesty rules every guide follows.

### If you want to run the live-generation loop yourself

This is the flow the "request a guide" box feeds into, and how all 103 draft
guides in this repo were produced:

1. Take `research/agent-brief.md` and fill in the app name/URL.
2. Give it to a research agent with web access and these instructions:
   official provider documentation only, read-only (no accounts, no
   submissions), return the structured 7-section report, flag everything it
   could not verify from official text.
3. Convert the report to the schema in `schema/guide-schema.md`, set
   `status: "draft"`, and save it as `guides/<id>.json`.
4. Validate the JSON (it must parse, carry every required schema key, and not
   duplicate an existing guide id), then add it to the site data.
5. Spot-check the highest-stakes claims against the official docs yourself
   (see `research/verification-log.md` for the pattern) before flipping the
   guide to `published`.

### If you are reviewing the code and data (this repo)

- `guides/*.json` is the source of truth: one JSON object per guide, all
  following `schema/guide-schema.md`. The hosted site embeds these files and
  renders generically from the schema, so adding a guide is adding a JSON
  file, no code changes.
- The site itself is a single static HTML page (HTML/CSS/JavaScript, hash
  routing, e.g. `#/guide/github`). To run it locally, export the artifact to
  a single `.html` file and open it in any browser, or serve the folder with
  any static file server. No build step, no server, no credentials.

## Key decisions

**Scope: the full library, built in waves on one documented pipeline.** The
original six were researched and reviewed by hand to cover the full
difficulty spectrum and the qualitatively different gates developers hit:
GitHub (no approval at all), Salesforce (no approval for integrations,
brutal optional marketplace review), Slack (no approval for OAuth,
workspace-count gate for listing), Notion (mandatory review before the first
user), Google (tiered verification where scope choice is timeline choice),
Spotify (instant setup, structurally closed launch for new builders). The
remaining 103 were then produced by running the same research brief in
parallel waves across CRM, payments, accounting, HR, support, marketing,
social, developer tools, and more, each converted to the schema, validated,
and added as `draft`.

**The guide is the product, and evidence is part of the guide.** Every guide
carries a difficulty rating, an active-work vs waiting time split, per-step
ownership (you / agent / either), blockers with clearances, and an evidence
block: what was tested, the exact sources, and what remains unverified. A
developer should never have to guess which claims are solid.

**Effort honesty as a design rule.** Provider-stated times are quoted;
anything else is labeled "not stated" or listed under Unverified. A 20-minute
form plus a 6-week review is never presented as "6 weeks of work". See
`schema/guide-schema.md`.

**Agents investigate; humans verify.** Research agents did the doc
spelunking (official docs only, read-only; where automated readers were
blocked, a live browser session read the pages instead, which is how the
Meta family, Twitch, and Eventbrite guides were sourced). Agent-generated
guides enter the library as `draft` until a human reviews them. The pipeline
is documented in `research/agent-brief.md` so the live-generation flow is
repeatable, not a trick.

**Static site, no backend.** Request-a-guide queues in the browser
(localStorage); generation happens in the operator's agent session. This
keeps the artifact shareable as a public link with no credentials anywhere
in the submission.

## Limitations

- **103 of the 109 guides are drafts.** They were generated by the documented
  pipeline from official provider documentation, schema-validated, and added
  with their sources and unverified items recorded, but they have not each
  had the individual human spot-check the six published guides received.
  Treat a draft's Unverified section as part of the guide, not fine print.
- **Read-only research.** No accounts were created and no setup flow was
  executed live, so "tested" in a guide's evidence means documentation
  review, stated plainly in each guide. Live walkthroughs (for example,
  confirming a provider's actual review turnaround against its stated one)
  are the obvious next verification step.
- **Providers change their docs.** Every guide carries a `lastVerified`
  date (2026-10-19 for the core six, 2026-10-20 for the expansion waves).
  Stale guides are worse than no guides; the library needs a re-verification
  cadence as it is maintained.
- **No automated generation endpoint.** The request flow queues for a human
  operator running the agent loop. A production version would wire this to a
  background agent with human review before publish.
- **US/English-centric.** Docs were read in English; regional policy
  differences (if any) are not covered.
